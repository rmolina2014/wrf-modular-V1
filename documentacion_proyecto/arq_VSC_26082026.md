# Arquitectura propuesta del sistema PGICH y WRF

**Fecha:** 2026-08-26  
**Proyecto:** Tesis de Maestría en Informática  
**Ámbito:** Ingesta EcoWitt, control de calidad, generación Little_R, OBS_DOMAIN101, WPS, WRF, validación e informes de experimentos.

---

## 1. Objetivo

El proyecto debe evolucionar desde un conjunto de scripts y ejecuciones manuales hacia un sistema modular Python capaz de:

- adquirir observaciones EcoWitt;
- aplicar control de calidad;
- generar Little_R y `OBS_DOMAIN101`;
- preparar y ejecutar WPS y WRF;
- ejecutar corridas nudged y control;
- validar resultados;
- producir métricas, gráficos e informes reproducibles;
- mostrar todo al usuario mediante un único panel de control.

La alternativa recomendada es la **Arquitectura Modular Python**, manteniendo Streamlit como interfaz de usuario y dejando la lógica científica y operativa fuera de `app.py`.

---

## 2. Diagnóstico del estado actual

Actualmente conviven tres sistemas parcialmente separados:

1. **Pipeline de investigación:** `pipeline_wrf.py`, namelists, conversores, validación y resultados.
2. **Sistema operativo histórico:** cron, descarga GFS, postproceso, correo y FTP, con scripts Python 2.
3. **Aplicación PGICH:** Streamlit para ingesta, limpieza, Little_R y visualización, sin controlar aún el ciclo WRF completo.

### Flujo actual

```text
API EcoWitt
    |
    v
JSON crudo
    |
    v
Limpieza y DataFrame
    |
    v
Little_R
    |
    v
OBS_DOMAIN101
    |
    v
GFS / WPS / met_em
    |
    v
real.exe
    |
    +--> WRF nudged
    |
    +--> WRF control
    |
    v
Validación
    |
    v
Métricas, gráficos e informe
```

### Problemas principales

- La tesis y el sistema operativo comparten el directorio de ejecución WRF.
- Las estaciones están duplicadas en varios archivos y scripts.
- `historico_a_obsnud.py` duplica la lógica de conversión y contiene una implementación antigua de `SYNOP`.
- Hay datos `obs_flat_*.json` generados sin un proceso reproducible claro.
- Existen contradicciones entre las versiones documentadas e instaladas de WRF/WPS.
- `fdda_end`, coeficientes y rutas no son uniformes en la documentación.
- La función `bilinear_interp()` de `valida_wrf.py` utiliza IDW, no interpolación bilineal estricta.
- Las métricas no conservan suficientemente el detalle estación-tiempo.
- El `README.md` está vacío.
- `pydeck` no está declarado en `pyproject.toml`.
- El `Dockerfile` instala `pyproject.toml` como si fuera `requirements.txt`.
- Existen scripts Python 2 y credenciales históricas dentro del código.
- `limpiar.bash` puede borrar archivos de una corrida compartida.

## 3. Opciones de arquitectura

### 3.1 Alternativa A: Consolidación mínima

Adecuada para finalizar la tesis con el menor cambio posible.

Acciones:

- mantener `pipeline_wrf.py`;
- eliminar la duplicación de `historico_a_obsnud.py`;
- centralizar el catálogo de estaciones;
- aislar los directorios de ejecución;
- agregar `manifest.json` por corrida;
- corregir Docker y dependencias;
- crear una plantilla estándar de informes;
- corregir la validación y los estados de ejecución.

**Ventajas:** bajo esfuerzo y menor riesgo de regresión.  
**Desventajas:** el orquestador seguirá siendo grande y difícil de mantener.

### 3.2 Alternativa B: Arquitectura modular Python

Es la alternativa recomendada para terminar los experimentos, automatizar el flujo y ofrecer un panel de control.

```text
Panel Streamlit
      |
      v
Servicios de aplicación
      |
      v
Pipeline modular Python
      |
      +--> Ingesta EcoWitt
      +--> Control de calidad
      +--> Little_R / OBS_DOMAIN101
      +--> WPS
      +--> real.exe / wrf.exe
      +--> Validación
      +--> Informes
```

**Ventajas:** responsabilidades claras, pruebas sencillas, reutilización desde CLI y Streamlit, mejor trazabilidad y mantenimiento.

**Desventajas:** requiere reorganizar imports, definir contratos entre módulos y agregar pruebas de integración.

### 3.3 Alternativa C: Plataforma de experimentos

Adecuada para ejecutar muchas fechas y matrices de sensibilidad.

Incluye:

- manifests YAML o JSON;
- registro en SQLite o CSV;
- ejecución por lotes;
- estados `planned`, `running`, `success`, `failed` e `invalid`;
- métricas consolidadas en CSV, Parquet o SQLite;
- dashboard comparativo.

**Ventajas:** permite escalar el número de experimentos.  
**Desventajas:** introduce complejidad adicional antes de estabilizar el pipeline.

### Decisión recomendada

Adoptar la **Alternativa B** e incorporar gradualmente elementos de la Alternativa C:

1. modularizar y estabilizar;
2. registrar manifests y estados;
3. automatizar matrices de fechas y parámetros.

## 4. Arquitectura modular propuesta

```text
src/pgich/
├── ingestion/
│   ├── ecowitt_client.py
│   └── gfs_downloader.py
├── quality/
│   ├── qc_rules.py
│   └── cleaner.py
├── formats/
│   ├── littler_writer.py
│   └── obsnud_writer.py
├── wps/
│   ├── namelist_manager.py
│   └── wps_runner.py
├── wrf/
│   ├── wrf_runner.py
│   └── run_directory.py
├── validation/
│   ├── spatial_interp.py
│   └── metrics.py
├── reporting/
│   ├── plot_generator.py
│   └── report_builder.py
└── experiments/
    ├── manifest.py
    ├── registry.py
    └── service.py
```

### Responsabilidades

- `ingestion`: API EcoWitt, histórico, GFS, reintentos, rate limiting y datos raw.
- `quality`: normalización, unidades, timestamps, rangos físicos, faltantes y outliers.
- `formats`: lectura y escritura de Little_R y `OBS_DOMAIN101`, incluyendo formato 105 y flags QC.
- `wps`: preparación del namelist WPS, verificación de GFS y ejecución de `geogrid`, `ungrib` y `metgrid`.
- `wrf`: preparación del namelist, directorio aislado, `real.exe`, `wrf.exe`, timeout y logs.
- `validation`: interpolación documentada, comparación estación-tiempo y métricas.
- `reporting`: tablas, gráficos, archivos JSON/CSV e informe Markdown.
- `experiments`: identificadores, manifests, estados y registro general.

El actual `pipeline_wrf.py` puede permanecer temporalmente como fachada de compatibilidad mientras su lógica se migra a estos módulos.

data/

runs/

        ├── input/
        ├── logs/
        ├── nudged/
        ├── control/
        ├── metrics/
        ├── plots/
        ├── manifest.json
        └── report.md

experiments/
├── manifests/

Los datos raw no se deben modificar. Cada transformación debe generar un nuevo archivo con fecha, fuente y versión del procesador.

Cada corrida debe tener su propio directorio. No se debe reutilizar el directorio WRF compartido entre la tesis y el sistema operativo.

## 6. Identificación y manifest de experimentos

Cada experimento debe tener un identificador estable, por ejemplo:

```text
EXP-20260812-00Z-SJ-NUDGE-TEMP0005
```

El `manifest.json` debe registrar:

```json
{
  "experiment_id": "EXP-20260812-00Z-SJ-NUDGE-TEMP0005",
  "status": "success",
  "date": "2026-08-12",
  "cycle": "00:00",
  "domain": "san_juan_15km",
  "wrf_version": "4.5",
  "wps_version": "4.5",
  "parameters": {
    "obs_coef_temp": 0.0005,
    "obs_coef_wind": 0.0005,
    "obs_coef_mois": 0.0005,
    "obs_twindo": 1.0,
    "obs_rinxy": 50.0
  },
  "inputs": {
    "observations_sha256": "...",
    "namelist_sha256": "...",
    "met_em_sha256": "..."
  },
  "execution": {
    "wps_status": "success",
    "real_status": "success",
    "wrf_nudged_status": "success",
    "wrf_control_status": "success",
    "validation_status": "success"
  }
}
```

Estados válidos:

- `planned`: definido pero no iniciado;
- `running`: en ejecución;
- `success`: completo y validado;
- `failed`: una etapa terminó con error;
- `invalid`: terminó, pero no cumple condiciones científicas.

Una corrida con `wrf.exe` incompleto no debe generar un informe marcado como resultado válido.

## 7. Panel de control Streamlit

El usuario final debe operar el sistema desde el panel sin manipular scripts, rutas internas, Little_R, `OBS_DOMAIN101` ni comandos WRF.

### Funciones del panel

#### Configuración

- fecha y hora del ciclo;
- dominio;
- fuente de observaciones;
- perfil nudged/control;
- coeficientes FDDA;
- ventana temporal;
- duración;
- entorno de ejecución.

#### Ejecución

- preparar observaciones;
- ejecutar WPS;
- ejecutar `real.exe`;
- ejecutar nudged;
- ejecutar control;
- validar;
- generar informe.

#### Seguimiento

Mostrar etapa actual, estado, duración, último mensaje, motivo del fallo y archivos generados.

```text
PLANIFICADO -> EJECUTANDO -> COMPLETADO
                         \-> FALLIDO
                         \-> INVÁLIDO
```

#### Análisis

- métricas generales;
- comparación nudged/control;
- resultados por estación, variable y hora;
- gráficos de dispersión;
- mapas de error;
- mejora porcentual frente al control;
- descarga de informe, CSV y JSON.

### Ejecución en segundo plano

WRF puede tardar minutos u horas. Streamlit debe iniciar un proceso independiente y consultar su estado, en lugar de bloquear la interfaz.

```text
Usuario pulsa Ejecutar
        |
        v
Se crea manifest.json
        |
        v
Se inicia un proceso independiente
        |
        v
El panel consulta estado y logs
        |
        v
Se muestran métricas e informe
```

La primera versión puede usar procesos locales controlados. Más adelante se puede incorporar una cola de tareas sin modificar los módulos científicos.

La aplicación debería llamar servicios como:

```python
experiment_service.create_experiment(config)
experiment_service.run_experiment(experiment_id)
experiment_service.get_status(experiment_id)
report_service.get_summary(experiment_id)
```

## 8. Informes científicos reproducibles

Los resultados numéricos deben almacenarse primero en:

```text
metrics/metrics.csv
metrics/metrics.json
report.md
```

Cada registro debe contener:

```text
experiment_id
valid_time
station
variable
unit
n_observations
bias
mae
rmse
correlation
model_mode
interpolation_method
observation_window_min
```

También se deben conservar:

- cantidad de observaciones rechazadas;
- motivos de rechazo;
- elevación de estación y del modelo;
- diferencia nudged-control;
- porcentaje de mejora;
- versión del código y configuración utilizada.

### Plantilla del informe

1. Identificación y objetivo.
2. Hipótesis.
3. Fecha, ciclo y dominio.
4. Versiones de WRF, WPS, Python y dependencias.
5. Datos de observación.
6. Configuración del namelist.
7. Cambios respecto al control.
8. Estado de WPS, `real.exe` y `wrf.exe`.
9. Validaciones de integridad.
10. Métricas por variable, estación y hora.
11. Gráficos.
12. Interpretación física.
13. Limitaciones.
14. Conclusión.
15. Comando exacto de reproducción.

El Markdown debe presentar los datos generados por el pipeline; no debe ser la única fuente de los resultados.

### Caso `gcoef` del 26 de agosto de 2026

El archivo `informe_exp_gcoef_26082026.md` debe conservarse como informe de diagnóstico preliminar. Las cinco ejecuciones de `wrf.exe` terminaron con el error `CAMtr_volume_mixing_ratio`. Por lo tanto, las estadísticas idénticas no permiten determinar qué valor de `obs_coef_temp` es óptimo.

La matriz de sensibilidad debe repetirse únicamente después de:

1. resolver la configuración de química;
2. verificar que `real.exe` y `wrf.exe` terminen correctamente;
3. confirmar todos los `wrfout` esperados;
4. ejecutar la validación completa;
5. generar automáticamente los informes.

## 9. Pruebas necesarias

### Pruebas unitarias

- catálogo único de estaciones;
- fechas y zonas horarias;
- conversiones de unidades;
- rangos físicos y valores missing;
- lectura y escritura Little_R;
- formato `OBS_DOMAIN101`;
- flags QC;
- métricas estadísticas;
- generación del manifest.

### Pruebas de integración

```text
JSON de prueba
    -> CSV validado
    -> Little_R
    -> OBS_DOMAIN101
    -> validación de formato
    -> métricas sintéticas
    -> informe
```

### Prueba de ciclo completo

Antes de ejecutar matrices de sensibilidad:

1. fijar una única versión oficial de WRF/WPS;
2. verificar todos los archivos `met_em`;
3. verificar los archivos auxiliares de química;
4. ejecutar `real.exe`;
5. ejecutar nudged y control en directorios separados;
6. confirmar los `wrfout` esperados;
7. calcular métricas;
8. generar el informe.

## 10. Plan de implementación

### Fase 1: Estabilización

- decidir versiones oficiales de WRF/WPS;
- separar directorios de ejecución;
- centralizar estaciones;
- proteger scripts de limpieza;
- retirar credenciales del código;
- corregir Docker y dependencias.

### Fase 2: Modularización

- convertir `src` en paquete Python;
- separar ingesta, calidad, formatos, WPS, WRF, validación e informes;
- mantener temporalmente compatibilidad con `pipeline_wrf.py`;
- eliminar la duplicación de `historico_a_obsnud.py`.

### Fase 3: Reproducibilidad

- crear IDs de experimento;
- generar manifests;
- registrar checksums, comandos y versiones;
- separar métricas, gráficos e informes.

### Fase 4: Automatización

- conectar los servicios con Streamlit;
- ejecutar procesos en segundo plano;
- mostrar estados y logs;
- permitir seleccionar configuraciones desde el panel.

### Fase 5: Experimentación masiva

- ejecutar múltiples fechas;
- automatizar sensibilidades de `obs_coef_temp`, `obs_coef_wind`, `obs_coef_mois`, `obs_twindo` y `obs_rinxy`;
- consolidar resultados en el registro;
- comparar experimentos desde el dashboard.

## 11. Decisiones técnicas recomendadas

1. Usar Python 3 como lenguaje oficial.
2. Mantener scripts Python 2 en un área legacy hasta migrarlos.
3. Usar un único catálogo de estaciones.
4. Ejecutar cada corrida en un directorio aislado.
5. Mantener los datos raw inmutables.
6. Separar métricas de gráficos e informes.
7. Generar manifests automáticamente.
8. Reutilizar los mismos servicios desde CLI y Streamlit.
9. No considerar válido un resultado con ejecución incompleta.
10. Versionar configuraciones y código, conservando checksums de datos pesados.
11. Usar el panel como interfaz de operación, no como lugar de implementación científica.

## 12. Resultado esperado

El usuario configura y ejecuta experimentos desde el panel. Internamente, el sistema produce:

```text
Configuración
    -> manifest
    -> datos validados
    -> entradas WPS/WRF
    -> ejecución aislada
    -> logs
    -> métricas
    -> gráficos
    -> informe reproducible
```

La decisión arquitectónica final es:

> El usuario configura y ejecuta experimentos desde el panel; el sistema registra, ejecuta, valida y documenta automáticamente cada corrida.

Esta organización permite terminar los experimentos con trazabilidad científica y deja una plataforma mantenible para nuevos casos de estudio y operación futura del PGICH.
